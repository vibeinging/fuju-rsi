# Fuju RSI 场景扩展方案

日期：2026-09-28
状态：场景清单与 Skill 路由已实现；社区场景代码接口仍为设计建议，不改变现有评分或采用条件

仓库约定的 `specs-workflow` 工具在当前环境没有可调用入口，因此本轮只保存设计建议，未建立规范任务状态。

## 结论

Fuju RSI 保持 **Skill 产品**：编码 Agent 在用户的项目里发现失败、提出改动、真实重跑、判断证据并交付。项目维护者只开发和持续维护**智能问数**场景；开源贡献者可以提供其他场景。扩展性采用“**共用实验内核 + 场景包 + 业务适配器**”三层；Fuju Trace 仍是独立的可选观测插件。

问数应作为仓库随带、默认可用的第一个**场景包**：含问数题集准备、完整结果结构、评分和诊断说明。社区场景既可先通过本仓库的评审与测试加入，也可以在稳定外部接口建立后单独发布；两条路径都不能各自实现一套候选选择和采用判定。

```text
编码 Agent 中的 Fuju RSI Skill
             │ 指导接入、提出和审查改动
             ▼
共用实验内核：来源分组、冻结、预算、验证次数、搜索、独立验收、报告
        │                                    │
        ▼                                    ▼
场景包（内建问数；社区可贡献其他场景）    业务适配器（项目自带）
题集/结果协议/判分/失败分类           运行真实程序、重置状态、读完整结果
        └────────── 实际运行结果 ──────────┘
             │
             └─ 可选观测：Fuju Trace；不可用时记本地状态日志
```

## 为什么要这样拆

当前代码已经有通用 `AgentSpec`、`optimize`、Benchmark、验收和报告，也有问数题集与结构化评分。但场景边界尚未形成稳定接缝：

| 当前接点 | 问题 | 建议落点 |
| --- | --- | --- |
| `workspace.py` 根据 `agent.kind == "ask-data"` 选择实验路径，并单独保存问数包和账本 | 第二个场景会继续增加分支；漏走分支还可能失去验证次数保护 | 由显式场景配置提供“运行前校验与预留”钩子，内核统一调用 |
| `verification.py` 根据 `kind` 把问数验证历史加入候选 | 场景证明散落在共用验收代码里 | 场景生成受限的证明材料，内核校验类型、版本、完整性并纳入候选摘要 |
| CLI 与 Skill helper 写死 `--ask-data-bundle`、`--validation-ledger` | 每增加场景都要改共用命令和文档 | 先保留现有命令；新增显式 `--scenario ask-data --scenario-config ...`，待迁移完成再收敛旧参数 |
| `AgentSpec` 要求 Python `runner/proposer/evaluator` | 非 Python 项目需要测试用 Python 胶水 | 保留 Python 适配；未来增加版本化本地命令协议，不要求业务程序在生产环境安装 RSI |

这些是扩展成本与误用风险，并非当前问数测试失败的证明。首版不要为了“通用插件平台”重写全部模块；先让一个真实问数项目跑通。

## 三层各管什么

### 共用实验内核：规则只能有一份

负责开发包与独立验收包的用途边界、来源与语义家族检查、完整基线、候选身份、预算和验证次数、固定条件、独立验收、采用判定、审计记录与报告的证据级别。核心只接受场景包返回的**已校验结果和有限的场景证明**，不接受场景包传入 `adoptable=true` 或自行放宽独立验收规则。

共用内核还必须确保：任何声明为可供采用的场景都使用同一套开发与验收隔离协议。未注册或未实现这些协议的 `kind="custom"` 可用于开发诊断，但不得仅凭总分授予采用资格；未知场景标识、版本不匹配、缺少验证账本时应明确失败，不能悄悄退回通用路径。

### 场景包：解释“什么算问对”

每个场景包有固定 `scenarioId` 和 `schemaVersion`，声明它接受的案例与结果格式、业务评分器、关键退步分类、可调整的产品对象和报告解释。问数场景包负责：

- 从业务来源登记和复核过的答案准备问数案例；同源改写继承用途。
- 要求答数结果包含所有轮次、完整列和行、重复行、排序、单位、精度与最终答复；只有预览时明确标为不完整。
- 区分答数、澄清、缺数据、运行异常、结果未保存及交付不完整。
- 固定评分器文件和数据/口径版本；数据或业务口径变化时重新建立基线。
- 说明指标、词典、项目规则、提示词等目标的正式来源，以及哪些变化必须先由业务方确认。

场景包可以给编码 Agent 提供参考文档和诊断建议，不能读取独立验收题来帮助生成候选，也不能把业务规则变化当作可搜索参数。场景包负责通用判分方法，不携带某个客户的私有案例、答案、密钥或生产连接。具体业务标准答案仍由使用者准备和复核。

### 业务适配器：对接用户已有程序

由用户项目持有，负责接收案例和候选，在隔离测试条件下启动真实单轮或多轮会话，确认候选确实传到最终调用，读取已保存的**完整**结果及最终答复，返回状态、用量和 Trace 关联。适配器还要明确超时、状态重置、共享配置恢复和结果分页读取规则。网络/认证/超时作为运行异常返回，答错作为业务结果交给评分器处理。

现有 Python `module:factory` 是第一种适配方式。Node、Go、Rust 等项目可先用薄的 Python 测试适配器调用原有命令或测试接口。若真实接入表明这层胶水成本很高，再提供本地命令协议；不需要先重写内核或引入常驻服务。业务应用上线后仍只加载普通提示词、配置或代码改动。

## 最小扩展契约

第一版只需要显式注册，不需要自动发现第三方包或插件市场。推荐配置概念如下（**示意，当前命令尚不支持**）：

```json
{
  "schemaVersion": 1,
  "scenario": {"id": "ask-data", "version": "1"},
  "developmentBundle": "evals/ask-data-dev-v1",
  "validationLedger": "evals/validation-history",
  "target": {"kind": "python-factory", "reference": "tests.ask_data_adapter:build_agent"},
  "candidate": {"kind": "prompt-file"}
}
```

内核按以下固定顺序调用场景接缝：

1. **载入前**检查场景标识、版本、配置完整性和包的用途；独立验收包必须先过角色守卫，再读案例正文。
2. **运行前**从冻结开发包核对来源、评分器和目标能力，预留整轮验证次数；失败、取消和重复候选不退还。缺完整结果读取能力时只做接入诊断。
3. **每次运行后**由适配器返回结构化结果，场景评分器给出分项与主分数；内核保存运行异常与业务失败的区别，并只向候选生成方开放训练明细、验证汇总。
4. **候选固定时**绑定候选、场景版本、场景证明、适配器/评分器身份、数据和口径版本、已见来源、验收政策。验收方再核对这些身份和独立来源；场景包不能覆写采用结论。

已在 Skill 中公开**场景清单、指南目录与贡献契约**，并提供只读发现脚本。它不加载场景代码。后续实现可先作为 Python 内部对象，并给贡献者一套协议测试。接受第二个真实场景并验证复用后，再将外部包加载接口标为稳定，并定义兼容和弃用周期。可选 Trace、提案器或报告样式可有各自接缝，但都不能成为场景判断正确性或授予采用资格的入口。

## 社区场景怎样贡献

一份场景贡献建议提供：`id/version` 与能力声明；案例输入和结果结构的校验；确定性的评分与失败分类；可调整对象及权限边界；给 Skill 使用的场景说明；没有私有数据的最小样例。若场景需要连接某个产品，再提供独立业务适配器示例。候选生成策略可以是可选材料；它不能成为场景安装的前提。

| 可由场景贡献者提供 | 由 RSI 核心统一执行 |
| --- | --- |
| 案例与结果格式、业务评分器、诊断分类、场景说明、合成或公开许可的示例 | 来源分组、冻结与用途守卫、验证次数预留、搜索预算、候选固定、独立验收、采用判定、证据报告 |
| 某个应用的测试适配器 | 验收数据访问边界和运行记录；适配器无法声明自己通过独立验收 |

建议先用代码评审接受仓库内的社区场景，形成第二种真正不同的场景并检验接口；等加载协议稳定后，再支持用户**显式选择**安装的外部场景包。外部包在开发机执行代码，必须展示包名、版本、来源和将调用的本地入口；不在打开仓库时自动扫描并执行插件。场景包升级后评分或结果含义变化，要冻结新 Benchmark 并重跑基线；不能沿用旧验收回执。

贡献验收应包含：一条真实入口的最小重跑、一条业务失败、一条运行异常、一条不完整输出；同源变体、验证次数耗尽、私有验收误读、版本/评分器漂移、关键案例退步等拒绝路径；打包后脱离开发目录运行。业务判分准确性还需该领域的独立复核，协议测试不能代替。仓库只随带虚构或有明确公开许可的样本，禁止提交客户题目、结果、凭据和 Trace 原文。

场景 PR 应说明适用问题、业务正确性的依据、适配器读取的完整结果、能力限制、例子与测试。维护者审核**扩展协议与证据边界**，场景作者或领域评审人负责业务口径；README 对未完成真实验收的场景要明确标记。具体投稿入口见仓库根目录的 `CONTRIBUTING.md`。

## 首版问数的产品体验

用户只需要给 Skill 现有问数程序位置、测试数据/口径、真实失败或案例，以及允许修改的范围。Skill 首先提供“**只评测原版**”，然后可“**比较两个现成版本**”，最后才做有限候选搜索。缺少参考答案时停在诊断与草案，不把未核对题纳入准确率。输出仍是普通改动、可读报告和恢复方法。

对外安装说明先展示 `fuju-tune` Skill 和问数默认场景；底层场景配置只在接入文档里出现。社区场景可共用同一 Skill 的实验方法，另放场景参考文档或场景 Skill，不复制防过拟合与验收规则。Skill 名称是否统一为 `fuju-rsi` 可在用户调用体验验证后再决定，迁移时保留旧入口。

## 建议实施顺序与验收

1. **先做真实问数闭环。** 在一个真实问数项目完成原版重跑、一个已有候选比较、完整结果读取、独立评分、普通文件交付与移除 RSI 后运行。合成 SQLite 示例只证明协议。
2. **建立内部场景接缝。** 将问数包校验、验证预留和候选冻结证明集中到一个显式场景对象；逐步去除 `workspace.py`、`verification.py`、CLI/helper 的散落 `kind` 分支。旧 `AgentSpec(kind="ask-data")` 和命令参数先保持兼容，迁移测试通过后再考虑弃用。
3. **增加负面验收。** 未知场景、错误版本、缺账本、场景或评分器漂移、只读到结果预览、同源变体跨集合、验收包误入开发入口时都必须拒绝继续或保持 `adoptable=false`；现有验收阈值不因重构改变。
4. **用社区场景验证扩展性。** 发布投稿契约和协议样例，接受一个确实不同的真实业务场景。如果仍需大量修改核心，调整接缝；对账通过后稳定外部包加载协议。是否提供 Go/Rust 独立 CLI 依据跨语言接入的实际成本决定。

完成标准分开记录：协议和单测通过、真实问数运行与结果完整、独立来源验收、产品按原有方式生效。前一项不能自动代表后一项。此方案与现有[问数评测设计](2026-09-28_ask-data-rsi-design.md)、[产品定位](2026-09-26_fuju-rsi-product-shape.md)和[跨语言备选方案](2026-09-28_fuju-rsi-cross-language-core.md)一致；本轮没有修改代码或放宽规则。
