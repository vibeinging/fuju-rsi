# Fuju RSI 应有的产品形态

日期：2026-09-26；Skill 产品定位修订：2026-09-28

## 2026-09-28 Skill 产品形态

**Fuju RSI 面向用户交付为一个可安装、手动唤起的 Agent Skill。** 用户在自己的编码 Agent 中提出目标，例如“检查并改进这个问数 Agent 的准确性”；Skill 理解当前项目，组织真实重跑与受控修改，最后交付可审查的改动和证据。首个场景只聚焦问数。

项目仓库继续存在，用于维护 Skill、可重复执行的脚本、评分和验收规则、适配器及测试；仓库本身不是用户需要理解的产品形态。当前已有的 `skills/fuju-tune/` 是这一方向的原型：可以复制使用，但还要另装 Python SDK，真实问数产品闭环尚未验证。未来是否把对外 Skill 名统一为 `fuju-rsi`，应连同安装和旧用法迁移一起处理，不靠改显示名宣称已经发版。

| 层 | 用户感受到的作用 | 责任 |
| --- | --- | --- |
| Skill | 对话式接入、理解业务目标、发现失败、提出受限候选、解释结论。 | 按需阅读项目和资料，指导流程与调用工具。 |
| 可执行工具 | 冻结题集、真实重跑、评分、预算和曝光次数、候选固定、生成报告。 | 执行稳定规则，不让一次对话的文字决定通过与否。 |
| 业务适配器 | 调用用户现有的 Python 或其他语言问数程序，并读取完整结果。 | 保持与实际业务路径一致；不成为线上依赖。 |
| 独立验收环境 | 持有未见来源和答案，比较固定候选。 | 与开发 Skill 的上下文、账号或 CI 实际隔离。 |
| Fuju Trace | 在可用时帮助定位执行问题。 | 可选观测；失败时不改变评分和验收。 |

Skill 的默认动作应是**先看现有项目和业务证据，再做一轮原版重跑**。只有可复核的失败与允许修改的范围明确后，才提出提示词或配置候选。`ask-data-benchmark` 的来源、口径、答案准备逻辑应成为问数流程的一部分；不要求用户先安装另一个 Skill。用户可以在“整理案例”“只诊断原版”“比较已有改动”“尝试改进”任一步结束。

防过拟合仍是硬边界：Skill 可以分析训练失败，验证集只用于有限次选方案；独立验收题不进入同一 Agent 的上下文。来源分组、答案版本、验证使用历史和验收资格由可执行工具检查，Skill 文本只能引导，不能自己签发“可信改善”。看过私有验收题后继续修改候选，下一次必须换新的独立来源。默认验收门槛不因产品改成 Skill 而改变。

第一版 Skill 产品的体验目标是：用户手动唤起一次，Skill 在当前 Python 问数项目中找到或建立真实测试入口，完成原版与一个已有候选的比较，给出报告和普通改动文件；需要采用结论时再由独立环境验收。安装后应能复制到另一个项目使用；停用 Skill 和测试工具后，业务产品仍可运行。当前还没有通过真实业务与跨项目安装验证，不能把它称为已经完成的产品。

实现语言留到这个体验被验证后决定。当前 Python 工具可继续承担确定性执行；非 Python 用户接入时再用项目原有命令或跨语言协议解决。Go 重写只是分发成本被证实过高时的备选。下面的旧章节保留技术与流程分析；与本节的产品入口冲突时，以本节为准。

## 2026-09-28 定位修订

**一句话：Fuju RSI 帮已有问数 Agent 的团队，基于真实业务结果持续改进系统，并判断一次改动是否有足够证据交付。** 首个产品场景是问数；以后是否扩展到别的 Agent，要由这一场景的真实接入效果决定。

首批使用者是负责问数 Agent 的开发者和测试负责人。他们已经有能运行的产品，常遇到“修好一批题、另一批题退步”“提示词改了但不知道真实结果是否变好”“同一道题反复试出了好分数”等问题。最终问数用户不会直接操作 RSI。业务产品只接收普通提示词、配置或代码改动；RSI 在开发与验收环节运行。

RSI 应交付一个可审查的**改进决定**：改了什么、哪些真实问题改善或退步、有没有运行异常、验证题用了多少次、独立验收是否通过、改动如何生效和恢复。可能的结论是“有可信改善”“当前没有改善”或“证据不足”；后两种也是有用结果，不能伪装成成功。

```text
已有问数系统 + 有来源的案例及复核答案
  → 运行原版，看到真实失败
  → 提出一个受限的改动并重跑比较
  → 固定改动，在独立环境验收
  → 交付普通改动文件、证据和恢复办法
```

产品的核心是四件事：**真实重跑、受控改动、防过拟合、可交付结论**。问数场景要求核对完整数据结果、多轮行为和最终答复，不能把 SQL 可执行、HTTP 成功或模型自评当作答案正确。来源关系、答案依据、数据快照和业务口径在改变时会使旧评测失效；同源改写和重复试验不增加独立证据。

现有评测平台已经提供数据集、实验比较与评分，例如 [Langfuse 的实验功能](https://langfuse.com/docs/evaluation/experiments/experiments-via-ui) 和 [LangSmith 的评测功能](https://docs.langchain.com/langsmith/evaluation-types)。所以“能跑一套题、比较两个提示词”本身不足以成为 Fuju RSI 的定位。我们的主张应由真实问数接入、来源和答案治理、验证曝光控制、独立验收及普通改动交付共同支撑；目前这些能力的代码覆盖程度不同，不能把设计主张当作已验证的产品优势。

**第一阶段的产品验收**：接通一个现有 Python 问数系统的真实运行路径，在固定数据和口径下完成原版与已有候选比较；报告必须包含完整结果、退步和异常。随后在真正隔离的环境中用新的来源验收固定候选，并证明交付文件在业务产品中生效且可恢复。合成样例和本机账本只证明协议或已知回归。自动提出候选可以后接；在它可靠之前，产品如实称为“评测与改进实验”，不宣传为无人监督的自动进化。

Skill 是首要使用入口；CLI、Python 接口和页面用于执行、接入或查看。Fuju Trace 是可选诊断工具。实现语言和是否需要跨语言分发，要在上述闭环与接入成本验证后决定；[跨语言核心方案](2026-09-28_fuju-rsi-cross-language-core.md)保留为备选设计，而非已确定的重写计划。以下章节是这一定位的展开；涉及尚未实现的能力仍是建议。

## 1. 定位

建议将 Fuju RSI 定位为：**用真实业务评测驱动 Agent 迭代改进的开发工具。**

用户提供现有 Agent、业务案例和允许修改的内容；RSI 组织基线、候选比较、独立验收与结果交付。改进最终成为产品原有的提示词、配置或代码。

核心价值是帮助开发者回答四个问题：哪里需要改、改了什么、是否真的改善、能否交付。没有发现可信收益也是完整结果。

本文件是基于当前代码提出的产品建议；没有修改实现、评分规则、采用条件或预算含义。当前没有可调用的 specs-workflow 工具，文档以待审阅建议保存，未建立规范任务状态。

## 2. 第一类用户与使用场景

首批用户建议聚焦已经有业务 Agent、真实执行入口和一些失败案例的开发者。近期把 AgenticData 问数流程做深，形成可以复用的接入样例，再扩展到工具调用和业务流程 Agent。

| 用户需要 | RSI 应提供 |
| --- | --- |
| 先看看系统哪里弱 | 固定案例的基线评测、分项结果、失败位置和证据。 |
| 手上已经有两个版本 | 直接比较版本，候选生成可省略。 |
| 想让编码 Agent 协助修改 | 只开放训练反馈，生成可审查候选，再真实重跑。 |
| 想证明改进可信 | 固定候选与条件，运行独立验收，报告收益、退步和证据范围。 |
| 想持续改善 | 通过已有 CI 或任务系统重复开发评测，显式进入验收与发布。 |

小批案例可以用于诊断和已知回归。它们的证据范围应明确，不因样本少就阻止用户开始，也不把回归通过升级成独立验收通过。

## 3. 用户看到的完整流程

```text
提供真实入口、案例、允许变化的内容、目标和预算
  → 检查案例与标准答案
  → 运行原版，形成基线
  → 诊断训练失败并提出候选
  → 训练题筛选，验证题选方案
  → 固定一个候选及代码、数据和评分条件
  → 独立验收
  → 交付普通文件、结果报告与原版恢复材料
  → 沿产品已有流程采用并检查实际生效
```

每个阶段可以单独使用。只评测、只比较已有候选、只生成题集、只导出历史报告，都应是完整用法。

用户入口以可复制的 Skill 为主，先通过现有 Python API 接通真实问数路径；跨语言 CLI 和本地页面按实际接入成本排序。页面可作为查看器，展示版本差异、失败分类、耗时与用量，以及实验是否完整、证据是否充分。安装和交付过程应保持简单，普通使用者只需理解原版、候选、评测和验收。

## 4. 四个稳定对象

### 任务

描述被测系统的真实入口、运行条件、状态重置方式和允许修改的范围。可以调用 Python 函数、现有命令或测试接口。黑盒能运行但不能配置候选时，仍可完成评测。

### 案例

保存输入、预期、判分规则、来源、语义家族、知识与数据版本、关键案例标记。生成题保持草案，标准答案经过复核后才能进入冻结包。开发与独立验收材料分开管理。

### 候选

保存相对哪个基线修改、修改内容、类型、适用条件和内容摘要。当前实现以完整提示词为候选；后续按阶段增加配置和代码差异。新接口应兼容当前 AgentSpec，而不是立即重写全部模块。

### 结果

同时记录业务质量、运行异常、耗时、实际已知用量、关键退步、运行完整性和验收证据。开发选出的候选、通过独立验收的候选、产品实际采用的版本分别记录。

## 5. 模块分工

| 模块 | 责任 | 默认形态 |
| --- | --- | --- |
| 接入 | 调用真实系统，注入候选，重置测试状态 | 外部适配器，业务运行时不依赖 RSI。 |
| Benchmark | 来源、答案依据、分组、版本和冻结 | 本地文件与校验接口。 |
| 评分 | 按业务契约比较结果，区分业务失败和运行异常 | 可插拔业务评分器。 |
| 候选生成 | 根据允许看到的训练反馈提出修改 | 文件候选、编码 Agent、可选模型适配器。 |
| 搜索 | 执行比较、消耗预算、选择候选、停止无效尝试 | 核心实验执行器。 |
| 独立验收 | 固定条件，管理题目使用历史，复验并形成可信回执 | 独立阶段，按声明的真实边界执行。 |
| 报告与交付 | 差异、结果、限制和恢复材料 | Markdown、JSON、普通文件。 |
| 观测 | 状态、关联 ID、故障定位 | Fuju Trace 可选插件，缺失或故障时日志回退。 |

问数场景吸收 `ask-data-benchmark` 的资料、口径、出题和答案准备逻辑。对外的 Fuju RSI Skill 协调整个改进任务；本仓库的可执行工具提供可重复的规则和记录。`fuju-trace` 提供可选的执行过程记录和查询。

详细业务 Trace 在授权的诊断流程中查看。RSI 普通观测只记录状态和计数，私有验收题与明细由验收侧保存。文件用途守卫、摘要和签名不能代替实际访问边界或证明业务答案正确。

## 6. 优化对象与目标

### 优化对象分阶段开放

1. 提示词：继续完善当前能力，支持比较用户已经准备好的候选。
2. 配置：例如检索参数、工具描述、流程开关和模型路由；每个适配器声明允许修改的字段与合法值。
3. 代码：在隔离副本中比较固定差异，运行原有测试和业务评测；交付普通代码补丁。

知识口径、标准答案和评分规则不是搜索变量。它们发生变化时创建新的评测版本、重新建立基线；不能与原口径混在一起报告收益。

### 目标按任务定义

问数可以优先追求准确率、关键题不退步；成熟系统可以追求质量满足约束时更低成本或更短延迟；工具 Agent 可以关注任务完成率和错误操作。

先声明必须满足的条件，再声明需要优化的指标。将质量、成本、时延分别报告。成本或用量未知时保持未知。

当前采用条件主要依据质量改善；成本/时延目标需要新的、预先固定且有版本的判定规则。这里提出扩展方向，不更改现有采用政策。

## 7. 搜索机制的演进

近期优先建立“失败驱动、修改范围明确、分阶段重跑”的策略：

1. 从训练失败中区分口径、检索、推理、工具、执行和交付问题。
2. 对提示词确实能影响的问题提出针对性候选；明确每个候选想修复什么。
3. 用训练失败题和相关已知回归先筛掉明显无效候选。筛选结果单独标记，不充当完整评测分数。
4. 对保留候选运行完整开发比较；验证信息用于选择方案，不将验证明细送给提案者。
5. 固定候选后，再用新的独立验收材料比较原版与候选。
6. 当候选重复、没有可改善问题、预算不足或外部条件漂移时结束并交付事实报告。

涉及随机模型时，比较应尽量采用相同条件和配对运行，记录波动。旧基线缓存只在条件一致且缓存用途明确时复用；不能让长时间之前的基线替代当前控制。分阶段筛选节省开发预算，但不减少最终验收的完整性要求。

maxCalls 当前只统计 runner/proposer 回调。将来可增加实际模型调用、Token、已知金额、运行时长和并发约束；需由业务或模型适配器提供计量和执行能力。回调上限、请求超时或本地取消都不能自动被描述成远端费用硬上限。

## 8. 当前实现与建议的差距

| 方面 | 当前已有 | 建议补充 |
| --- | --- | --- |
| 实验执行 | AgentSpec、runner/proposer/evaluator、提示词候选、基线与训练/验证重跑 | 更直接的单独评测和已有版本比较入口。 |
| 可信验收 | Benchmark 冻结、用途守卫、来源历史、候选身份、回执和采用判断 | 简化接入路径，清楚展示证据级别和不能采用的具体原因。 |
| 业务接入 | AgenticData 和公开基准适配材料 | 在当前目标系统上实跑；区分适配器测试、历史记录和真实业务收益。 |
| 候选范围 | 完整提示词文本 | 后续逐步支持结构化配置与代码差异。 |
| 目标 | 质量评分，耗时与可选用量记录 | 明确目标与约束；成本/时延比较需要新增判定协议。 |
| 题集准备 | Benchmark 通用接口；外部 Ask Data Skill | 问数题集导入与评分适配，标准答案复核和开发/验收交接。 |
| 使用体验 | Skill、CLI、SDK、报告、可选页面 | 把接入、基线、比较和交付做成连续路径，减少用户手写胶水代码。 |
| 持续运行 | 有限后台包、任务账本、显式交付 | 通过宿主 CI/任务系统接入，保留验收和发布责任边界。 |

## 9. 近期优先级

### 第一阶段：真实问数闭环

- 选定一个真实 AgenticData 测试入口，证明候选能到达最终调用。
- 接通 ask-data-benchmark 产物与 RSI，落实 SQL 结果、多轮、澄清、空集和重复行评分。
- 用户可以从运行原版开始，再比较一个候选，得到失败明细、报告和普通提示词差异。
- 需要独立验收时，再接入真正独立的数据与执行边界。
- 完成普通配置实际生效、原版恢复，以及移除实验工具后继续运行的检查。

### 第二阶段：有效搜索

- 增加失败分类、受限修改、候选去重和开发阶段筛选。
- 用真实任务评估搜索成本与收益；没有改善时清楚结束。
- 记录模型随机波动、运行异常和条件漂移，避免挑选偶然好分数。

### 第三阶段：扩展对象与持续改进

- 按实际场景引入配置候选和代码差异。
- 引入经过评审的成本/时延目标与判定规则。
- 再完善宿主任务系统、CI 和可选查看器集成。

近期交付标准应是：一个真实系统能接入、能评测、能比较、能解释证据，并交付真正生效且可恢复的改动。可信收益必须来自实际评测；流程正确和协议测试通过单独报告。
