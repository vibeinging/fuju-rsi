# Fuju RSI 跨语言核心方案

日期：2026-09-28

状态：Skill 产品下的跨语言工具分发备选；先验证真实问数产品闭环，尚未决定重写核心

## 有条件的技术建议

Fuju RSI 的首要产品入口是 Skill。本文件只讨论 Skill 背后执行工具在多语言项目中的分发与调用方式，不改变[产品形态文档](2026-09-26_fuju-rsi-product-shape.md)确定的入口优先级。

如果真实接入证明跨语言分发是主要障碍，可以将 Fuju RSI 做成独立命令行产品，考虑用 **Go 实现下一版核心**，以本地进程协议接入 Python、Node、Go、Rust 等业务程序。Python 可以保留为可选适配器，不成为非 Python 用户的前提。应先完成问数场景的原版评测、已有候选比较和独立验收，再决定是否重写核心；自动生成候选排在后面。

这个选择是针对当前产品形态的判断，不表示 Go 在所有评分或存储任务上优于 Rust。Fuju Trace 继续作为可选观测插件；没有 Trace 时写本地状态日志。业务产品运行时不依赖 RSI。

## 为什么要改

当前 `AgentSpec` 要求业务提供 Python 的 `runner`、`proposer`、`evaluator` 回调。问数判分、来源账本、候选冻结和验收也在 Python 包里。对 Node、Go、Rust 项目，开发环境必须额外安装 Python，并写一层 Python 胶水。Python 的源码身份、函数快照和异常格式还渗入候选包，跨语言后不能直接沿用。

RSI 的耗时主要在业务系统、模型和数据库重跑。把核心改成编译语言的主要收益是分发、运行边界和多语言接入，不应承诺问数响应或模型调用明显提速。

| 方案 | 适合之处 | 当前代价 |
| --- | --- | --- |
| 继续用 Python | 已有完整代码和测试，能最快接现有 Python 系统。 | 其他语言的用户仍需 Python 环境和回调胶水。 |
| Go 核心 + 外部适配器 | 单独分发可执行文件，进程、超时和并发调度直接；适合离线实验工具。 | 需要重做核心和兼容验证，数值、摘要、文件锁等不能照搬 Python 默认行为。 |
| Rust 核心 + 外部适配器 | 适合将来需要可嵌入库、统一低层协议或精细资源控制时。 | 当前 RSI 以流程编排为主，重写和后续适配成本更高，短期收益有限。 |

**若决定做跨语言主程序，Go 是当前优先备选，不做 Go/Rust 双核心。** Rust 可以写业务侧适配器，也可以在未来有明确的嵌入需求时重新评估。Fuju Trace 的实现语言不要求 RSI 使用同一运行时。产品定位与第一条真实问数闭环见[产品形态文档](2026-09-26_fuju-rsi-product-shape.md)。

## 接入协议

RSI 调用用户声明的本地命令，使用带 `schemaVersion` 的 JSON 消息交换数据。第一版可以用一次请求、一次应答的 stdin/stdout 协议；stderr 仅作受限诊断。命令参数作为数组传入，不经 shell 拼接。业务接入程序负责：

1. 按案例建立隔离会话或重置状态；将候选提示词或配置按产品原有方式加载。
2. 真实执行一轮或多轮问数；返回任务状态、已保存的完整结果、最终答复和可核对的运行标识。HTTP 成功、任务成功或模型自报正确都不代替业务结果。
3. 按固定规则提供业务行为和交付判分所需的证据。通用表格判分留在 RSI 核心；特殊业务判分可由独立命令完成，其文件和版本进入验收快照。

消息要区分 `run_error`、`protocol_error`、`business_failure` 和成功结果。大结果用受控的结果文件加内容摘要返回，不能只返回预览；比较前必须确认完整行数、列、重复行、排序、精度、单位和轮次。每次调用记录案例、候选、数据快照和口径版本的身份，但普通观测日志不写原题、提示词、答案或原始输出。

**数值是迁移的硬点。** Go 将未指定类型的 JSON 数值解入 `interface{}` 时默认可能成为 `float64`；问数中的大整数和高精度小数不能这样比较。协议优先规定十进制数值的文本表示及单位/精度规则；解析时保留原始数字文本，需要算术比较时使用明确的任意精度实现。`null`、`0`、空字符串和空集合也必须分别处理。

插件不依赖 Go 的 `.so` 动态插件机制。Trace 适配器、模型提案器和业务 runner 都通过版本化进程协议或内置适配器接入；这样各业务语言与主程序可独立构建和升级。Go 官方文档也说明 `plugin` 的平台和构建一致性限制。

## Python 业务程序怎么用

**现在**可以继续使用现有 Python 包与 `AgentSpec`，不需要为了这份设计改业务代码。**将来 Go 核心上线时**，Python 程序只需一个薄的测试适配入口：Go 命令行调用用户项目原有虚拟环境中的 `python -m your_app.rsi_adapter`；适配入口读一条 JSON 请求，调用已有问数函数，再把任务状态、已保存的完整结果和最终答复写成一条 JSON 响应。它不实现 RSI 的来源分组、验证次数、候选选择或验收规则。

```text
fuju-rsi 命令行（Go）
  → 用户已有的 Python 虚拟环境和测试适配入口
  → 用户现有问数函数、数据库与结果存储
  → 结构化运行结果返回 RSI 判分
```

配置中应把命令写成参数数组，明确指定该项目的 Python 解释器或虚拟环境，不依赖全局 `python` 恰好指向哪个环境。适配入口只在开发评测或独立验收时运行；产品部署时仍按原方式运行 Python 应用。可以提供可选的 Python 协议辅助库来减少样板代码，但 Go 主程序和非 Python 用户不依赖它，也不长期保留两套各自做判分和验收的核心。适配入口需与真实业务调用路径一致，不能用模拟返回值代替。

## 防过拟合规则必须原样迁移

- 原题来源和语义家族先登记，再分 train/validation/holdout；同源变体不跨用途。训练只给候选生成器详细反馈。
- 验证次数在任何业务运行前预留，失败、取消和重复候选也计入；跨实验、跨题集版本保留同源使用史。
- 候选固定时绑定候选内容、运行命令和适配器文件、评分规则、数据快照、已见来源及环境版本。迁移现有 Python 摘要时，必须定义规范序列化规则和跨语言测试向量，不假定两种 JSON 编码产生同一摘要。
- 独立验收运行在另一个账号或 CI 环境，开发程序拿不到私有题；本机账本、签名或文件角色标记都不能单独证明独立性。默认采用门槛和关键案例规则保持现状，不因换语言而放宽。
- 超时和取消只约束本地调度，不能称为模型费用硬上限。结果必须区分开发提升、独立验收通过和产品实际生效。

## 最小迁移路径

1. **先冻结协议和对账样例**：从现有 Python 实现整理来源分组、空集、重复行、大整数、小数、多轮、验证次数、取消、候选冻结、验收重叠等样例。明确与当前工作区格式的兼容策略。
2. **先写 Go 的只评测与已有候选比较**：读取冻结开发包，调用业务命令，按现有规则判分、记账和出报告。暂不迁入自动提案器和页面。
3. **先接用户现有的 Python 问数程序**：通过其原有虚拟环境启动适配入口，在隔离数据上对比原版/候选的真实持久化结果与最终答复。合成题只能证明协议和已知回归。随后再接 Node 或 Go 示例，验证确实不依赖 Python。
4. **接独立验收**：在分开的环境中运行固定候选，验证来源隔离、完整结果、回执及产品实际加载。没有新的独立题时保持 `adoptable=false`。
5. **达到功能对账后切换发行入口**：提供 macOS/Linux/Windows 的对应可执行文件和校验值；Python 适配器只作为可选包。旧 Python 工具在迁移期间保留，避免在规则尚未对账时直接替换。

交付验收应同时通过跨语言协议测试、与旧规则的对账测试、真实问数重跑和独立验收流程检查。现有 233 项 Python 测试只证明旧实现的当前基线，不能证明 Go 版本已经等价，也不能证明问数收益。
