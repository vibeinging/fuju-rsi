# Fuju RSI 的问数评测设计

日期：2026-09-28
状态：设计主线；来源分组、结构化判分和验证次数账本已实现，真实业务接入待验证

## 结论

`ask-data-benchmark` 在 Fuju RSI 中应该成为**内建的问数评测场景**。它负责把业务知识、真实问题、数据快照和答案依据组织成可重复执行的评测活动，并把评测结果交给 RSI 的候选比较和独立验收机制。

Fuju RSI 的目标产品形态是 Skill，问数是首个场景。Skill 面向用户补问业务口径、整理材料、分析失败并解释结果；项目中的可执行工具负责案例版本、判分、验证使用历史和运行记录。这些硬规则不能靠 Skill 文本约定或一次性的格式转换来保证。当前 `fuju-tune` 是可复制的原型，真实问数接入仍待验证。

**最高优先级是防止过拟合。** 问数场景很容易通过大量同义改写、反复查看验证题、调整标准答案或针对固定数据写特殊规则获得高分。RSI 只有在固定规则下、用独立来源问题验证了一个固定候选，才可以报告对未见问题的改进；其余结果须准确标为诊断、开发比较或已知回归。

## 反过拟合是系统主线

| 环节 | 必须控制的事 | 能得出的结论 |
| --- | --- | --- |
| 题目来源 | 先登记原始问题、来源、语义家族和关联材料，再按来源分配用途；之后生成的改写继承分配结果。 | 防止把同一原题变体当作独立样本。 |
| 标准答案 | 独立复核并固定口径、数据快照和评分规则；口径改变后旧答案失效。 | 避免根据产品输出或候选效果修 gold。 |
| 训练 | 候选生成者可看详细失败，新增反例也进入训练或已知回归。 | 发现和修复具体问题。 |
| 验证 | 只用于有限次数的候选选择；给提案者汇总，记录看过的版本及尝试次数。 | 在开发分布上选择候选；不能称为未见题收益。 |
| 独立验收 | 验收方持有未向提案者开放的来源与答案；先固定唯一候选、评分器、环境和政策，再成对比较原版与候选。 | 在本次独立来源和固定条件下判断是否有可信改善。 |

一个原题及其几十道同义题仍是一个来源组。重跑三遍提高同一题评分的稳定性，不产生三个独立来源。关系检查与模拟数据可以查一致性，但不能凭它们声称覆盖了新的真实业务来源。

验证集即使只返回总分，反复试不同候选也会逐渐泄漏选择信号。应限制同一冻结验证集的选择轮数，把每次使用写入跨实验记录；长期反复调优时更换新的来源组。这个限制属于产品策略建议，具体次数需在实施前确定。验收集查看失败内容后可用于诊断，但下一轮改进时它已成为已知数据，需准备新的独立验收来源。

独立验收需要实际的数据和账号/CI 边界。角色字段、文件摘要、签名和本地使用账本能防止正常流程中的误用，不能让同一操作者已经看过的题重新变成未见题，也不能证明业务答案正确。报告必须同时写明独立来源组数、变体数、运行重复次数、使用历史和验收边界。

## 用户看到的流程

```text
业务规则 + 原始问数问题 + 测试数据 + 真实问数入口
    ↓
登记来源并分配用途 → 确认口径和数据版本 → 生成同源案例草案 → 复核标准答案
    ↓
冻结开发评测集 → 运行原版 → 分层判分与定位失败
    ↓
提出限定范围的候选 → 训练题检查 → 验证题选择
    ↓
固定候选和运行条件 → 独立验收 → 交付普通配置/代码及证据
```

用户可以在“生成题集”“只评测原版”“比较两个已有版本”任一步结束；这些都是完整用法。没有标准答案的案例可供诊断和口径澄清，不能进入准确率分母。

## 产品内的两层

### RSI 通用层

保留现有 Benchmark 冻结、runner/evaluator、实验账本、候选选择、预算、独立验收和报告能力。通用层只认识案例、预期、结果、来源组、版本和证据，不写死 SQL、数据库驱动或 AgenticData 的接口。

### 问数场景层

提供四种具体能力：

1. **案例构建**：从原题、业务规则和已知失败生成有意义的改写、维度/时间/公式变化、多轮与边界案例。
2. **答案核对**：对确定性结果保存参考计算、数据快照、列/行/重复/排序/精度/单位约定；对“应澄清”“缺数据”保存行为依据和评分规则。
3. **运行适配**：通过业务已有入口启动新会话、逐轮执行、读取真实保存结果和最终答复；连接、数据准备及模型费用由具体适配器管理。
4. **问数诊断**：根据实际结果与可用 Trace，定位语义理解、指标/字典映射、Schema 检索、SQL 生成与审核、执行、结果保存和最终答复等阶段。

Ask Data 场景层保存在 RSI 仓库中，由对外的 Fuju RSI Skill 引导用户使用。案例准备、评分和验收逻辑作为工具实现，Skill 负责决定何时调用、如何解读证据；安装 Skill 不应把业务产品绑到 RSI 的线上运行时。

## 关键数据对象

| 对象 | 必要信息 | 用途 |
| --- | --- | --- |
| 业务上下文 | 指标定义、词典、范围/粒度/单位规则、来源与版本 | 明确问题在当前业务中的含义。 |
| 数据快照 | 测试数据或可复现的源库版本、相关表和准备方式 | 保证参考计算与产品运行可比。 |
| 案例 | 原题来源、语义家族、问题或有序轮次、目标行为、训练/验证/验收用途 | 防止同源改写跨集合；支持多轮。 |
| 标准答案 | 参考 SQL 或独立方法、实际结果、复核证据、匹配规则及版本 | 判分依据；生成成功或 SQL 能执行均不自动等于已验证。 |
| 运行结果 | 每轮任务状态、实际执行 SQL 与结果、最终答复、耗时/用量、Trace 关联 | 同时判断计算、交付和运行可靠性。 |
| 候选 | 允许修改的提示词/配置/代码、基线身份、差异和摘要 | 可重跑、可审查、可恢复。 |

当前通用案例可承载冻结后的问数题；问数模块已增加来源先分组、数据和口径版本校验、结构化表格与多轮判分。真实问数 runner、完整结果读取和行为判分仍由业务适配器提供。

### 案例关系图

问数题库宜记录原题及其变化关系，而不只存一个平面问题列表。原始业务问题是来源节点；每次改写标注变化类型和受影响的意图字段：

- 仅换说法且意图不变：可以共享已复核的标准答案，同时作为表达鲁棒性案例。
- 改时间、维度、条件、公式或输出：产生新的案例和标准答案；保留与原题的关系，便于检查能力迁移。
- 连续追问：记录轮次、沿用的上下文和被修正的条件，在同一会话执行。
- 有数学或集合关系的变体：记录关系约束及适用前提，作为额外一致性检查。

所有来自同一原题的变体沿用来源身份；来源先分配用途，生成变体后继续继承该用途。关系图可以为 RSI 的通用 `Example` 输出扁平的冻结案例；它自身保留生成依据、谱系、曝光历史和答案失效链。语义关系需要业务复核，不能仅凭模型生成的标签认定两个问题等价。

## 题目生成与答案规则

先将原题整理为结构化意图：业务对象、指标、维度、过滤、时间、粒度、公式、排序和输出。自然语言相似不代表问题等价：只有这些决定答案的部分相同，改写题才可共用标准答案。改变时间、维度、公式或返回列时，建立新的预期。

测试覆盖优先来自真实高频问题和真实失败，再补会区分错误逻辑的边界数据。例如 COUNT 与 COUNT DISTINCT、总体比率与比率均值、一对多 JOIN、NULL 与 0、空集和列头、并列排名、千行预览与全量结果、多轮改口径。

标准答案有三个状态：草案、已复核、因口径或数据变化而失效。已复核需要可追溯的业务依据、实际计算和至少一种语义复核证据，例如人工核算、独立计算或能识别错误计算的固定数据。系统不能用被测 Agent 的输出自证正确。

除逐题固定结果外，可以支持**有条件的关系检查**：同义题应同结果；加过滤后的集合应符合明确定义的子集关系；同一粒度的可加指标分组之和应等于总量。关系检查必须先验证业务前提，不能把非可加比率机械相加。它可扩大回归覆盖，但不能替代需要精确值的独立验收答案。

## 判分与失败定位

问数每个案例至少区分：

- **计算结果**：实际持久化结果与标准答案是否一致；比较完整列、行、重复、排序、精度和单位。空集必须包含成功状态、结果字段和列结构；解析失败不能算空集正确。
- **最终交付**：用户收到的答案是否完整、范围正确、未把部分预览说成全量。
- **行为**：问题歧义时是否按已确定的规则澄清；数据不足时是否明确说明。
- **运行**：超时、审核要求重写、执行失败、保存失败和最终交付失败分别记录，不能把运行异常当作业务正确率的证据。

RSI 通用评分器仍可接收一个事先定义的主质量分数；上述维度同时保留，便于查错和检查关键案例。不能为了提高总分临时改变评分规则、忽略超时题或删掉失败轮次。多轮题需逐轮核对，整题通过必须满足预先声明的所有必要轮次。

Trace 用于定位实际链路的首次可见偏离。没有 Trace 时仍能用结果判分，只降低归因置信度。RSI 自身普通观测仍只记录状态和计数；题目、提示词、gold 与私有验收明细留在对应评测环境。

## 改进逻辑

RSI 的优化单位应是业务程序实际加载的**版本化改动包**，而不是固定等于提示词。移动问数 Benchmark 是一个具体例子：产品侧可能调整正式指标配置、业务词典和项目规则；评测题、Gold 和评分器属于衡量改动的依据，不是为了提分而调整的目标。候选应绑定原始文件和版本、允许修改的范围、差异、生成后配置、隔离运行条件和恢复方式。多个文件共同产生一种业务行为时，要作为同一个候选版本验证。

移动项目的正式指标以 `metric-definitions.xlsx` 及同步的 Markdown 为依据，词典补充和项目规则分别位于 `config/source/term_context.json` 与 `config/source/agent_rules.md`；生成配置由项目准备脚本产生。这是该项目的适配信息，其他社区场景应声明自己的可调整对象和正式来源。

必须先判定改动是否保持业务口径。已核实的别名或等价表达澄清可在原数据快照、Benchmark 和 Gold 下比较。公式、范围、时间、NULL/0、阈值等含义发生变化时，先取得业务确认，再更新正式来源、Gold 与 Benchmark 版本，并在新规则下重建原版基线；不能把跨口径分数差称为优化收益。评分器或 Gold 错误也需独立修正并同时重跑原版与候选。问数场景 Skill 的[调整对象说明](../../skills/fuju-tune/scenarios/ask-data/targets.md)给出具体执行边界。

评测完成后先分类失败，再决定可修改对象：

| 发现 | 合理候选 |
| --- | --- |
| 叫法、枚举值映射错 | 通用业务词典或映射配置。 |
| 相关表列未召回 | Schema 检索策略、提示或索引配置。 |
| 聚合粒度、JOIN、条件错 | SQL 生成/审核提示词或实现。 |
| SQL 结果正确但答复漏行、漏单位 | 最终答复规则或结果呈现代码。 |
| 业务定义本身冲突或缺失 | 先由业务方确定口径，再更新上下文、答案及基线。 |
| 数据库或任务运行失败 | 修运行链路并重跑，不将其归为提示词收益。 |

当前提示词支持自动搜索和独立验收；词典、项目规则和指标上下文支持 `compare-files` 的已给定文件候选开发比较，配置独立验收尚未开放。文件候选声明可改字段和版本，以独立目录运行并交付原版恢复材料。检索配置和代码候选仍需后续接入。**正式业务规则含义和评测标准不是可随意搜索的参数。** 经业务确认的规则修订如果改变了正确答案，需要新建 Benchmark 版本和重建基线；普通同义词映射修正若不改变答案，可在原答案契约下比较。

训练题的详细失败可用于提案；验证题用于选择候选；独立验收题由独立流程掌握。按原始来源和语义家族分组后再划分用途，同源变体不跨集合。查看验收失败后继续调优，需要新的未见验收材料；旧题转为已知回归。开发分数提升只说明开发条件下改善，不能授予采用资格。

每个候选都应记录它看过哪些来源、哪些反馈和多少次验证汇总。候选相同或只针对已知题做特例时停止尝试；先用训练题和已知回归淘汰明显失败的方案，再消耗验证题。固定验收前不得根据验证或验收结果修改 scorer、答案、关键案例标记或回归阈值。确需修评测器时，单独版本化规则并在同一新规则下重建原版基线。

运行条件须配对：原版与候选用相同数据快照、业务配置、模型条件、超时和预先确定的评分方式；随机模型按既定次数重复，避免挑一次最好结果。现有验收采用来源组等权比较，不把同源变体或重复运行当作更多独立样本。关键案例退步、运行异常和证据不足要分别报告。小批已知题可用于调试，但不得靠降低默认组数来把它描述为充分的独立证据。

## 与当前代码的接点

- [`benchmark.py`](../../src/fuju_rsi/benchmark.py) 已有 v2 开发/验收包、来源组和冻结接口，可继续作为版本边界。
- [`core.py`](../../src/fuju_rsi/core.py) 当前按完整提示词生成候选，并对 train/validation 重跑；Ask Data 运行适配与评分可先通过 runner/evaluator 接入。
- [`verification.py`](../../src/fuju_rsi/verification.py) 与 [`acceptance.py`](../../src/fuju_rsi/acceptance.py) 已有固定候选、重复运行、独立来源组和采用条件；问数场景不应绕开这些边界。
- [`holdout_registry.py`](../../src/fuju_rsi/holdout_registry.py) 已记录本机项目的验收题使用历史；它覆盖的目录和权限范围应明确写进报告。
- 现有 AgenticData 适配材料只覆盖有限合成题及已准备的模型入口。已知合成题适合协议检查和回归，真实业务收益需要另行实跑并建立可信来源与答案。

问数模块现已将来源登记与用途继承、跨实验验证次数、旧版开发来源令牌接入候选冻结。来源身份仍由资料准备者如实登记；本机账本不能阻止另建目录或篡改文件。真正的私有验收隔离仍取决于独立环境。

这里不建议先修改通用验收阈值或引入常驻服务。优先验证一条真实业务路径的案例、结果解析、评分和候选生效；数据量或证据不足时准确报告限制。

## 第一版范围

1. 先建立来源身份、案例关系和用途分配；同源变体保持同组，准备真正独立的验收来源。
2. 选一个现有问数应用和稳定测试数据；实现真实单轮/多轮 runner、完整结果解析和领域评分器，并固定口径与数据快照。
3. 为原题、澄清、空集、重复行、比率和多轮准备小型有来源案例；把标准答案复核和版本失效做成明确状态。
4. 先交付“只评测原版”和“比较用户给的两个提示词”；明确区分训练、验证和独立验收证据。
5. 再接训练反馈驱动的候选生成，并限制验证重复选择；由实际隔离的验收流程检查固定候选。

第一版成功标准是：真实系统能重跑；对题目/数据/口径改变有正确失效处理；结果报告能解释每个分母和失败；交付的改动在业务系统原有方式下实际生效并可恢复。业务准确率提升需要独立实验观察，不由设计文档或离线协议测试推断。
